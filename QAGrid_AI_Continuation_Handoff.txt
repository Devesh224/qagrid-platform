5. ARCHITECTURE AND BUSINESS RULES

Text architecture:
QA engineer or Postman -> Environment Registry API -> Registry PostgreSQL
QA engineer or Postman -> Reservation Scheduler API -> Scheduler PostgreSQL
Reservation Scheduler API -> HTTP GET Registry environment by ID
Design-only future extensions: Test Execution and Notification.

The Registry's "available environments" route means ACTIVE and HEALTHY. It does not inspect reservation slots. Scheduler's availability route checks a time interval.

Reservation creation:
1. Validate UUID, requester, purpose and timezone-aware ISO 8601 timestamps. Start must be in the future and end after start.
2. Scheduler calls Registry over HTTP with a two-second timeout.
3. Registry environment must exist and be ACTIVE and HEALTHY; UNDER_MAINTENANCE is nonbookable.
4. Scheduler queries its own DB for an overlap.
5. It inserts a CONFIRMED booking in a DB transaction.
6. PostgreSQL exclusion constraint makes conflicting concurrent inserts safe. Scheduler maps SQLSTATE 23P01 to HTTP 409.

Use half-open intervals [start_time, end_time): an existing start < requested end AND existing end > requested start means overlap. 10:00-11:00 and 11:00-12:00 are adjacent and allowed. Only CONFIRMED reservations block. CANCELLED and COMPLETED remain as history but do not block. An availability GET is advisory, because another request may reserve before a subsequent POST. Do not claim concurrency safety from the pre-insert query; the DB constraint is the safety mechanism.

The Scheduler schema creates btree_gist and uses an exclusion constraint on environment_id equality plus tstzrange(start_time, end_time, '[)') overlap, restricted to status='CONFIRMED'. There is no cross-database foreign key; environment_id is a logical reference validated via HTTP.

Cross-service consistency limit: Registry status can change after Scheduler's successful lookup. The prototype rejects new requests according to the Registry response at lookup time but does not automatically cancel existing bookings when maintenance begins. Do not describe this as a distributed transaction or guaranteed atomic state across both services.

6. API SUMMARY

Registry (root path /api/v1/environments):
POST /                          create, 201; duplicate name 409
GET /                           list/filter/paginate
GET /available                  ACTIVE and HEALTHY list
GET /{environment_id}           details, 404 if missing
PATCH /{environment_id}         update descriptive fields
PATCH /{environment_id}/status  ACTIVE, INACTIVE, UNDER_MAINTENANCE; maintenance reason required for maintenance
PATCH /{environment_id}/health  HEALTHY, UNHEALTHY, UNKNOWN

Scheduler (root path /api/v1/reservations):
POST /                          create; 201 success, 404 missing environment, 409 nonbookable or overlap, 422 invalid input, 503 Registry unavailable
GET /                           list/filter/paginate
GET /availability               environment_id, start_time, end_time; 200 with available true/false for a bookable environment
GET /{reservation_id}           details, 404 if missing
PATCH /{reservation_id}/cancel  idempotent cancellation unless already COMPLETED
PATCH /{reservation_id}/complete after the end time, unless CANCELLED

Both expose GET /health/live and GET /health/ready. Readiness queries the service's own table. Both expose generated OpenAPI at /docs. New environments start with health UNKNOWN; change to HEALTHY before making a reservation. FastAPI validation errors use its standard detail format.
